# ollama-mcp-delegate

**English: [README.md](README.md)** · [日本語環境での挙動](docs/ja/japanese-environment.md) · [設定リファレンス](docs/ja/configuration.md)

**Claude Code をオーケストレーターのまま**にしつつ、**機械的な作業はローカルの Ollama モデルに任せる** MCP サーバーです。ファイル編集、コードの調査、lint のトリアージ — これらの本文が Claude のコンテキストに一切入らないので、同じ結果をより少ないトークンで得られます。

```
  あなた ──▶ Claude Code (Anthropic)      ← 判断・計画・レビュー
              │
              │  パスと指示だけ            (小さい)
              ▼
        ollama-mcp-delegate  ──▶ Ollama ──▶ qwen2.5-coder / qwen3-coder
              │                      │
              │                      └── ファイル読み込み・grep・編集をすべてローカルで
              │
              ▼  検証ゲート (構文チェック + プロジェクト固有のチェック)
              │
              │  レシート: 変更ファイル, +12/-4, gate=pass  (小さい)
              ▼
        Claude Code
```

## 核となる考え方

**委譲は、処理を一段増やすのではなく、本文を追い出すものでなければならない。** このサーバーのツールは *パスと指示* だけを受け取り、ファイルの中身は決して受け取りません。返すのは *レシート* であって、コードではありません。委譲の指示を書くために Claude がファイルを読んでしまったら、その時点でトークンは既に消費されており、何も節約できていません。

もう一つの考え方が、出力を信頼できるものにしています。**決定的なゲートを通過するまで、成功とは報告しない。** 素の Claude Code と同等の結果になるのは、ローカルモデルが賢いからではありません。タスクが狭く、結果が機械的に検査可能で、チェックに失敗したら自動でロールバックしてエスカレーションするからです。

## これは何ではないか

- Claude の**置き換えではありません**。`ANTHROPIC_BASE_URL` で Claude Code 全体を Ollama に向けるのは別物で、それはハイブリッドを作るのではなく Claude を取り除く行為です。
- Claude Code のサブエージェントをローカルで動かす方法では**ありません**。サブエージェントの `model:` フロントマターは Anthropic のティアしか受け付けません。本サーバーはその代わりに用意された正規の接続点です。
- アーキテクチャ、デバッグ、曖昧な判断の役には**立ちません**。期待値は**委譲可能な作業で 30〜60%、難しい思考では約 0%** の削減です。これ以上を約束する説明は、数え方を間違えています。

## インストール

Python 3.10 以上と [Ollama](https://ollama.com) が必要です。検索には [ripgrep](https://github.com/BurntSushi/ripgrep) があれば使い、無ければ純 Python のフォールバックに切り替わります。これは Windows で効いてきます — `rg` が Git Bash の中にだけ入っていて、システムの PATH には無いことがよくあるためです。

```bash
git clone https://github.com/Rikiza89/ollama_mcp
cd ollama_mcp
uv venv && uv pip install -e .

ollama pull qwen2.5-coder:7b     # fast ティア
ollama pull qwen3-coder:30b      # deep ティア (約 18 GB)
```

Claude Code への登録は一度だけで、全プロジェクトに効きます。

```bash
claude mcp add -s user ollama-local -- /abs/path/to/ollama_mcp/.venv/bin/ollama-mcp
# Windows: ...\ollama_mcp\.venv\Scripts\ollama-mcp.exe
```

そのうえで、呼び出しごとの承認プロンプトを消します。`~/.claude/settings.json` に次を追加してください。

```json
{
  "permissions": {
    "allow": [
      "mcp__ollama-local__local_edit",
      "mcp__ollama-local__local_explain",
      "mcp__ollama-local__local_verify",
      "mcp__ollama-local__local_status"
    ]
  }
}
```

これをやらないと毎回承認を求められ、三日で使わなくなります。

## Claude に実際に委譲させる

ここが一番飛ばされやすく、そして投資が回収できるかどうかを決める工程です。放っておくと Claude は自前の `Edit` ツールを使います — Claude の立場からはその方が速くて確実だからです。使うなと明示する必要があります。プロジェクトの `CLAUDE.md` に次を追加してください。

コピーしてそのまま貼れる日本語版は **[docs/ja/delegation-policy.md](docs/ja/delegation-policy.md)** にあります。

```markdown
## ローカル委譲ポリシー

`ollama-local` MCP サーバー経由でローカルモデルが利用できます。作業をそちらに回してください。

`local_edit` に委譲する (ファイルを先に Read しないこと):
- docstring、コメント、コメントの翻訳
- 型注釈、リネーム、既に決定済みのシグネチャ変更
- ボイラープレート、テストの雛形、複数ファイルへの同一パターン適用
- フォーマットと lint の修正

ファイルそのものではなく「事実」が欲しいときは、Read/Grep の代わりに `local_explain` に委譲する:
- 「X はどこで定義されているか」「モジュール Y は何をするか」「どの呼び出し元が Z を渡しているか」

lint / 型チェックを Bash で走らせる代わりに `local_verify` に委譲する。

自分で処理するもの:
- アーキテクチャと設計判断
- デバッグ、根本原因の分析、曖昧なもの全般
- 複数ファイルにまたがる推論、セキュリティに関わるコード
- 変更内容を一段落で言い切れない編集

ツールが ESCALATE を返したら、作業ツリーは変更されていません。自分で対応してください。
```

## ゲートの設定

各プロジェクトのルートに `.ollama-mcp.toml` を置きます。実質的に重要なのは `[gate]` だけで、他はすべて実用的なデフォルトがあります。

```toml
[gate]
commands = [
  ["ruff", "check", "--quiet", "."],
  ["python", "-m", "pytest", "-x", "-q", "tests/unit"],
]
timeout_s = 180

[models]
fast = "qwen2.5-coder:7b"
deep = "qwen3-coder:30b"
fast_num_ctx = 16384
deep_num_ctx = 32768
keep_alive = "10m"

[limits]
max_iterations = 12
request_timeout_s = 900
max_local_retries = 1

[sandbox]
deny = [".git", ".env", "node_modules", ".venv", ".pem"]

[i18n]
language = "auto"   # "auto" | "en" | "ja"
```

設定ファイルは読み込み時に検証されます。未知のキーや型の合わない値があると、ファイル名とキー名を示してサーバーが起動時に停止します。黙ってデフォルトに落ちて、三回目の委譲で初めて気づく、ということは起きません。全項目の説明は [docs/ja/configuration.md](docs/ja/configuration.md) にあります。

設定ファイルが無い場合、ゲートは「変更されたファイルの構文チェック」＋「自動検出したプロジェクトのチェック」（`ruff`、`tsc --noEmit`、`cargo check`、`go build`）にフォールバックします。

ゲートは**速く**保ってください。委譲した編集のたびに実行され、失敗した場合はローカル再試行の後にもう一度実行されます。

## 言語

`[i18n] language`（または環境変数 `OLLAMA_MCP_LANG`）が、ローカルモデルに送るプロンプトとレシート内の説明文の言語を決めます。デフォルトの `auto` は呼び出しごとに指示文から判定し、判定できなければマシンのロケールにフォールバックします。つまり、ロケールが英語のノート PC でも、日本語で書いたタスクには日本語のプロンプトが使われます。これが日本の開発者にとっては一番多いケースです。

ステータストークンは**決して翻訳されません**。`APPLIED`、`NOT APPLIED`、`ESCALATE`、`PASS`、`FAIL` はプロトコルです。世の中の `CLAUDE.md` の委譲ポリシーはどれも「ツールが ESCALATE を返したら作業ツリーは変更されていない」と書いており、このトークンを訳してしまうとそれらが静かに壊れます。翻訳されるのは、トークンの周囲の文だけです。

日本語環境では、他にも自分で踏み抜かないと分からない挙動がいくつか変わります — 非 UTF-8 コンソール、BOM、分解済みファイル名、そして CJK でのトークン単価です。**[docs/ja/japanese-environment.md](docs/ja/japanese-environment.md)** を参照してください。

## ツール

| ツール | 代わりに使うもの | 返すもの |
|---|---|---|
| `local_edit` | Read + Edit | 変更ファイル、`+n/-m`、ゲートの判定 |
| `local_explain` | Read + Grep | `path:line` の引用付きの密度の高い回答 |
| `local_verify` | Bash での lint / 型チェック | PASS、または整理された失敗一覧 |
| `local_status` | — | 稼働状況、導入済みモデル、これまでの削減量 |

ツールは意図的に 4 つだけです。ツールスキーマはリクエストのたびに永久に再送されるので、12 個のツールベルトは、それが生み出すはずの節約を食い潰します。

## ツール呼び出しチャンネルを無視するローカルモデル

Ollama は、テンプレートがツールスキーマを描画できるモデルすべてに `tools` ケイパビリティを広告します。ところが実際には、`qwen2.5-coder` を含む多くのモデルが、ネイティブのチャンネルではなくメッセージ本文に呼び出しを出力します — 素の JSON、```json フェンス、あるいは `<tool_call>` タグで囲んだ形で。

未処理のままだとこれは *「モデルが何もせずに終了した」* と全く同じに見えます。診断としては間違っており、不要なエスカレーションを生みます。

そこでサーバーは、ネイティブのフィールドが空のときに限り本文をパースします。ただし実際に提供しているツール名である場合だけ実行します — モデルが設定ファイルを引用しただけの JSON が実行されることはありません。書き込み系ツールを一度も呼ばずに DONE と報告した場合は、エスカレーションの前に一度だけ的を絞った指摘を返します。

## 本当に削減できているのか

呼び出しのたびに、プロジェクト内の `.ollama-mcp/metrics.jsonl` に 1 行が追記されます。`local_status` がそれを要約します。

```
savings so far: {"calls": 41, "succeeded": 34, "escalated": 7,
                 "estimated_tokens_avoided": 118400,
                 "tokens_spent_on_receipts": 4900,
                 "median_duration_s": 22.4}
```

`estimated_tokens_avoided` はその名のとおり推定値です — ローカルモデルが読み、その結果 Claude が読まずに済んだファイル本文の量です。この推定は文字種を考慮します。ASCII のソースは約 4 文字で 1 トークン、CJK は約 1 文字で 1 トークンとして数えます。日本語を chars/4 で数えると、委譲が最も効くリポジトリでこそ削減量を約 3 分の 1 に過小評価してしまうからです。請求書ではなく傾向線として扱ってください。

正直な指標はエスカレーション率の方です。**委譲の 3 分の 1 以上がエスカレーションするなら、委譲する作業の種類を間違えています。**

## ハードウェアについて

`qwen3-coder:30b` は MoE（合計 30B、アクティブ約 3B）で、Q4_K_M で約 18 GB です。これは重要な性質で、密な 30B と違い、大半のレイヤーがシステム RAM に載っていても実用的な速度を保ちます。`qwen2.5-coder:7b`（4.7 GB）は 16k コンテキストなら 8 GB VRAM に丸ごと収まります。fast ティアがデフォルトで、deep ティアが呼び出しごとのオプトインなのはこのためです。

RTX 5050 Laptop（8 GB VRAM）+ Ryzen 7 260 + 32 GB RAM での実測、4 つの関数を持つモジュールに Google スタイルの docstring を追加する作業:

| | fast (`qwen2.5-coder:7b`) | deep (`qwen3-coder:30b`) |
|---|---|---|
| docstring 編集 | **ゲート失敗**、ロールバック、エスカレーション | **適用成功**、+37/−0、gate pass |
| 所要時間 | 39 秒 | コールド 61 秒 / ウォーム 26 秒 |
| リポジトリ Q&A (`local_explain`) | 正答、3 秒 | — |

1 行目は設計の失敗ではなく、設計が働いている様子です。7B は複数箇所の厳密な文字列一致編集を安定してこなせず、構文ゲートが壊れた出力を捕まえ、作業ツリーはバイト単位で復元されました。**fast ティアは調査と単一箇所の編集に使い、編集が複数箇所に及ぶ時点で `tier="deep"` に切り替えてください。**

両方のモデルを常駐させないこと。`keep_alive` は最後に使ったモデルを保持します。deep ティアならこれは 18 GB の RAM を意味します。

`num_ctx` についての注意: Ollama のデフォルトは 4096 で、それを超えると**黙って切り捨てます**。本サーバーは常に `num_ctx` を明示的に送ります。値を上げる場合、KV キャッシュがモデルの重みと VRAM を奪い合うことを忘れないでください。

## 安全性

ローカルモデルは実際の作業ツリーに書き込みます。ガードは順に次のとおりです。

1. すべてのパスは解決されたうえで `workspace_root` の内側に閉じ込められ、トラバーサルは拒否されます。
2. `[sandbox] deny` が `.git`、`.env`、鍵ファイル、`node_modules`、その他あなたが列挙したものをブロックします。
3. 最初の書き込みの前に元のファイル内容がメモリ上にスナップショットされ、ゲートが失敗したら自動で復元されます。
4. `local_explain` と `local_verify` には書き込みツールが一切渡されません。
5. 編集は各ファイルの既存の改行コードとバイト内容を保持します。ファイル全体が CRLF に置き換わることはなく、非 ASCII のコメント（日本語、アクセント付き文字）は非 UTF-8 コンソール、BOM、レガシーな Shift-JIS のいずれでも壊れません。

それでも git リポジトリの中で実行してください。メモリ上のロールバックはゲート失敗をカバーしますが、「モデルが間違ったことに成功した」場合はカバーしません。
